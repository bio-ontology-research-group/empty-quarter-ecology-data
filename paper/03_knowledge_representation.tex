\subsection{Knowledge representation}\label{ontology}

We present the resource as a modular RDF knowledge base that connects sampling sites, physical samples, laboratory measurements, experimental producedures, sequencing datasets, and taxonomic assignments. Rather than representing these data as independent tables, we encode their relationships explicitly. This allows users to trace an observation to the sample, site, or process it describes, and query related data across different stages of the study (Figure~\ref{fig:kg_model}).

\input{kg_model}

The graph separates a shared terminology module, which defines the classes and relationships used to describe the data, from modules containing the actual study records. In ontology terminology, these correspond to the Tbox and ABox, respectively. Shared identifiers connect the modules (Table~\ref{tab:modules}), while the Semanticscience Integrated Ontology (SIO) provides general classes and relationships for representing entities, processes, and measurements \cite{sio}. The terminology module declares 333 classes (297 defined for this project and 36 from other ontologies), 20 object properties, and 35 datatype properties written in OWL \cite{owl2}. 

To support interpretation and reuse, KG v3.0.1 provides English
definitions for all 342 project terms, recorded using SKOS and IAO
definition annotations. Claude Sonnet 5.5 drafted the definitions from term labels,
axioms and dataset context, and OpenAI Codex assisted with automated
review and editing. We distribute the definitions, model provenance
and review records with the release. The terminology module imports
four reference ontologies, and the observation modules are linked as
parts of the dataset.


\subsubsection{Representing provenance}

The data model rests on two distinctions. First, physical materia (a soil sample, a DNA extract), the process applied to it (extraction, sequencing), and the data those processes produce (a FASTQ dataset) are represented as separate entities connected by inputs and outputs. Second, a measured value is kept separate from the property it quantifies and from the entity that has the property. Together, these distinctions record where every value came from.

\textbf{Shared vocabularies and external ontologies.} We reuse established terms that exist in an external ontology where relevant (Table~\ref{tab:external_resources}). Because these identifiers are shared with other resources, the data can be queried and compared alongside other datasets. We retain original labels and values with the mapped identifiers.

\textbf{Measurements.} We represent measurements separately from the biological or environmental qualities they describe. For example, the temperature of a site is a property (quality) of that site (Listing~\ref{lst:ttl_temp}). A measurement process carried out during a particular site visit produces a value for that property. The graph links the value to the quality, the quality to the site, and the measurement process to the visit. This separates what was measured from how, where, and when it was measured. It also allows the same quality to be measured repeatedly, for example on different visits, without ambiguity.

Each value holds its numerical reading and, where documented, its unit. The ShEx shape assigned to each type of value specifies its datatype and unit requirements, which differ for counts, measurements with units and measurements whose units were not documented.

Listing~\ref{lst:ttl_temp} shows this representation for a field temperature measurement. The measurement process is part of a site visit, the visit targets the site, and the process produces a value of 20.7~\degree C, which quantifies the temperature of that site. Because SIO provides relations in both directions between a value and its quality, users can start a query from either and retrieve each measurement together with its sampling context.

\begin{lstlisting}[caption={Field temperature and its visit provenance.},label={lst:ttl_temp},basicstyle=\ttfamily\scriptsize,frame=single]
@prefix rak: <https://rubalkhali.science/kb/RAK_> .
@prefix sio: <http://semanticscience.org/resource/SIO_> .
@prefix pato: <http://purl.obolibrary.org/obo/PATO_> .
@prefix uo: <http://purl.obolibrary.org/obo/UO_> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

# Measurement process
rak:P000001 a rak:0000006 ;            # type: field measurement process
    sio:000068 rak:3000001 ;           # is part of -> site visit
    sio:000229 rak:4000001 .           # has output -> measured value
 
# Site visit
rak:3000001 a rak:0000003 ;            # type: site visit
    sio:000291 rak:1000001 .           # has target -> sampling site
 
# Measured value
rak:4000001 a rak:0000010 ;            # type: measurement value
    sio:000221 uo:0000027 ;            # has unit -> degree Celsius
    rak:2000003 "20.7"^^xsd:double ;   # numerical value
    sio:000215 rak:5000001 .           # is measurement value of -> quality
 
# Quality of the site
rak:5000001 a pato:0000146 ;           # type: temperature (PATO)
    sio:000011 rak:1000001 ;           # is attribute of -> sampling site
    sio:000216 rak:4000001 .           # has measurement value -> value
\end{lstlisting}

\textbf{Taxonomy.} A taxonomic label can denote different taxa across databases and releases, and a taxon can be referred to by several labels \cite{balvovciute2017silva}. To ensure consistent identification, we retained SILVA assignments for each ASV and linked it to either a validated NCBI Taxonomy identifier or a project-specific identifier when no suitable NCBI Taxonomy identifier was found.

Each SILVA assignment describes the organism across seven ranks from domain to species, and may include an additional species prediction and a confidence score. We used the species name from the rank assignment in the knowledge graph and kept the additional species assignment as an annotation. Before mapping, we removed prefixes from taxon names and explicitly recorded missing and unclassified ranks.

For each SILVA assignment, we checked for a candidate NCBI identifier from a fixed NCBI Taxonomy release (OBO Foundry NCBITaxon r2025-03-13 built from NCBI Taxonomy 1 March 2025). A candidate was only accepted if the identifier exists in that release, its rank matches, its name matches the SILVA name or a documented synonym, and its parent taxa in NCBI match identifiers already accepted for the higher ranks of the same assignment. When no candidate met these criteria, the name was given a project-specific identifier, which refers to a unique combination of rank, name, and parent taxa. As a result, users can therefore query each ASV by its original SILVA assignment or by its NCBI or project identifier.

\subsubsection{Formal patterns}

The relationships described above are defined formally as Description
Logic patterns \cite{dlhandbook}. Each pattern specifies which kinds of entities
can be related and how, giving a precise description of the graph's
structure that users can rely on when writing queries. The same patterns
define the constraints checked during structural validation
(Section~\ref{subsec:schema_def}). In the notation below, $\sqsubseteq$
means ``is a subclass of'', $\sqcap$ means ``and'', $\exists R.C$ means
``has at least one relation $R$ to a member of class $C$'', and
$\forall R.C$ means ``all relations $R$ point to members of class $C$''.
Section~\ref{methods:graph_examples} gives the corresponding RDF examples.

\textbf{Sampling.} A sampling process targets a site and produces a collection of samples, and each sample is also linked directly to its site.

\begin{small}
\begin{align}
	\label{eq:sampling}
	\text{SamplingProcess} & \sqsubseteq \text{Process} \\
	\text{Sample} & \sqsubseteq \text{MaterialEntity} \\
    \text{SampleCollection} & \sqsubseteq \text{Collection} \sqcap
        \forall \text{hasMember}.\text{Sample} \\
	\text{SamplingProcess} & \sqsubseteq \exists
                                 \text{hasTarget}.\text{Site} \sqcap
                                 \exists
                                 \text{hasOutput}.\text{SampleCollection} \\
	\text{Sample} & \sqsubseteq \exists \text{isDerivedFrom}.\text{Site}
\end{align}
\end{small}

\textbf{Protocols.} Each field or laboratory step is recorded as the execution of a
protocol, with the material or data it used and produced.

\begin{small}
\begin{align}
	\label{eq:protocol}
	\text{ProtocolExecution} & \sqsubseteq \text{Process} \\
	\text{Protocol} & \sqsubseteq \text{InformationContentEntity} \\
	\text{ProtocolExecution} & \sqsubseteq \exists
	    \text{isSpecifiedBy}.\text{Protocol} \\
	\text{ProtocolExecution} & \sqsubseteq \exists
	    \text{hasInput}.\text{Entity} \sqcap \exists
	    \text{hasOutput}.\text{Entity}
\end{align}
\end{small}

\textbf{Taxonomic abundance.} A value quantifies the abundance of a taxon and belongs to a dataset
produced by a bioinformatic workflow from a sequence dataset.

\begin{small}
\begin{align}
	\label{eq:taxabundance}
	\text{BioinformaticWorkflow} & \sqsubseteq \text{Process} \\
	\text{TaxonomicDataset} & \sqsubseteq \text{Collection} \\
	\text{BioinformaticWorkflow} & \sqsubseteq \exists
	    \text{hasInput}.\text{SequenceDataset} \sqcap \exists
	    \text{hasOutput}.\text{TaxonomicDataset} \\
	\text{TaxonomicDataset} & \sqsubseteq \forall
	    \text{hasMember}.\text{AbundanceObservation} \\
	\text{AbundanceObservation} & \sqsubseteq \text{Quantity} \sqcap
	    \exists \text{isMeasurementValueOf}.\text{AbundanceQuality} \\
	\text{AbundanceQuality} & \sqsubseteq \exists
	    \text{isAttributeOf}.\text{Taxon} \\
	\text{AbundanceQuality} & \sqsubseteq \exists
	    \text{hasMeasurementValue}.\text{AbundanceObservation}
\end{align}
\end{small}

\textbf{XRF.} Laboratory XRF measurements take a soil sample as input, whereas field measurements target a sampling site, and both produce concentration values.

\begin{small}
\begin{align}
\label{eq:xrf}
\text{XRFProcess} & \sqsubseteq \text{MeasurementProcess}
  \sqcap \exists \text{hasOutput}.\text{Concentration} \\
\text{LabXRFProcess} & \sqsubseteq
  \text{XRFProcess} \sqcap \exists
  \text{hasInput}.\text{SoilSample} \\
\text{FieldXRFProcess} & \sqsubseteq
  \text{XRFProcess} \sqcap \exists
  \text{hasTarget}.\text{SamplingSite} \\
\text{Concentration} & \sqsubseteq \text{Quantity} \sqcap
  \exists \text{isMeasurementValueOf}.\text{AnalyteQuality}
\end{align}
\end{small}

\textbf{Sequencing.} DNA extraction, library preparation and sequencing are linked through their shared inputs and outputs, so that each sequence dataset can be traced back to its soil sample.

\begin{small}
\begin{align}
	\label{eq:sequencing}
	\text{DNAExtractionProcess} & \sqsubseteq \text{ProtocolExecution} \\
	\text{DNAExtractionProcess} & \sqsubseteq \exists
	    \text{hasInput}.\text{SoilSample} \sqcap \exists
	    \text{hasOutput}.\text{DNAExtract} \\
	\text{LibraryPreparationProcess} & \sqsubseteq \text{ProtocolExecution} \\
	\text{LibraryPreparationProcess} & \sqsubseteq \exists
	    \text{hasInput}.\text{DNAExtract} \sqcap \exists
	    \text{hasOutput}.\text{AmpliconLibrary} \\
	\text{SequencingProcess} & \sqsubseteq \text{ProtocolExecution} \\
	\text{SequencingProcess} & \sqsubseteq \exists
	    \text{hasInput}.\text{AmpliconLibrary} \sqcap \exists
	    \text{hasOutput}.\text{FASTQDataset} \\
	\text{FASTQDataset} & \sqsubseteq \text{Dataset} \\
	\text{FASTQDataset} & \sqsubseteq \forall
	    \text{hasMember}.\text{SequenceRead}
\end{align}
\end{small}

\textbf{Sequence quality control.} Quality metrics are attached to the FASTQ dataset they describe.

\begin{small}
\begin{align}
	\label{eq:qc}
	\text{SequencingQCProcess} & \sqsubseteq \text{Process} \\
	\text{SequencingQCProcess} & \sqsubseteq \exists
	    \text{hasInput}.\text{FASTQDataset} \sqcap \exists
	    \text{hasOutput}.\text{QCMeasurementValue} \\
	\text{QCMeasurementValue} & \sqsubseteq \text{Quantity} \sqcap
	    \exists \text{isMeasurementValueOf}.\text{QCQuality} \\
	\text{QCQuality} & \sqsubseteq
	    \begin{aligned}[t]
	    &\exists \text{isAttributeOf}.{}\\[-0.25ex]
	    &\text{FASTQDataset}
	    \end{aligned}
\end{align}
\end{small}

\subsubsection{OWL and RDF implementation}\label{subsec:owl_rdf}

The modules are generated with Groovy scripts using OWL API v5.1.20 \cite{owlapi}.
Keeping the shared terminology separate from the study data allows each to be updated and checked independently
\cite{cuencagrau2008modular}. The asserted graph is stored in OpenLink Virtuoso \cite{virtuoso} which supports SPARQL queries over the whole resource. Release KG v3.0.1 serves the asserted triples.

Some facts follow from the asserted statements without being stated
explicitly; for example, a sample of a subclass of soil sample is also a
soil sample. A separate workflow derives such facts with a rule program v1.5.0 of positive RDF rules and stores them in a separate graph, so that recorded statements can be distinguished from those that are derived. The rules cover equivalent classes and properties, subclass and subproperty hierarchies, instance types, property domains and resource-valued ranges, and inverse, symmetric, and transitive properties. For property chains, one rule is generated for each non-empty finite chain in the loaded schema, including chains with inverse properties. Further rules handle value restrictions, existential restrictions (classified from
existing links and typed targets), universal restrictions (applied to
existing targets), intersections, union membership and enumerated classes.
The rules do not create new RDF terms. The schema audit lists the imported
ontologies and the OWL constructs not covered by the rules.

Each rule adds only triples that are absent from both the asserted and the
inferred graph, working in batches, and is repeated until it adds no new
triples. The complete set of rules is applied repeatedly until a full pass
adds no triples; at that point, all consequences of the rule program have
been computed (its least fixed point). The run records the rule text, the
lists of data partitions, the number of inferred triples, software
versions and input identifiers. It stops with a failure if a query result
is truncated, an SQL error occurs or the maximum number of passes is
reached. After the run completes, separate checks search for conflicts
between disjoint or complementary classes, members of \texttt{owl:Nothing}
and incompatible control roles. The inference therefore covers only this
rule set and these checks.

\subsubsection{Validation}\label{subsec:schema_def}
We checked the generated graph for structural integrity with Shape Expressions (ShEx) and for logical consistency with an OWL reasoner. Both checks detect errors in how the data are represented, but they do not establish biological correctness. Results are reported in Section~\ref{valid}.

\textbf{Structure.}
ShEx \cite{shex} is a schema language that checks whether selected
entities have the required types and properties, how many values each
property has and whether the values have the correct datatype. We defined
shapes for all main entity types: sampling sites, soil samples, DNA
extracts, sequencing datasets, measurements, quality-control records,
laboratory control materials, control roles, laboratory batches, sequences
detected in controls, soil pH measurements, values and sessions, and
taxonomy mappings. For example, the sample shape requires a replicate
type, a label, a source identifier and a link to the site from which the
sample was derived, and the DNA concentration shape checks the numerical
value, the unit (ng/\textmu L) and the links to the measured quality and
process.
 
The shapes have known limits. The site shape checks that a geometry is
present, but not that it is valid WKT with correct coordinate syntax. The
XRF-process shape requires an input or target, but checking that it
belongs to the correct class requires an additional check. The shapes are
open, so entities may have properties beyond those declared, and
additional types are accepted regardless of how they were asserted. Test
data that deliberately violate the shapes confirm that the failures
reported in Technical Validation are detected.
 
A Shape Map assigns each set of entities (e.g.\ all sampling sites) to its
shape. During deployment, each newly generated data module is checked, and
deployment stops if a required property is missing (e.g.\ the coordinates
of a site) or a value has the wrong datatype. Validation used the Apache
Jena ShEx library v4.10.0, called from Groovy scripts. The multi-gigabyte
taxonomy data are too large for this in-memory check; instead, the file is
parsed in full with an independent Turtle parser and checked with a
streaming validator that covers every link between classification
process, dataset, quality and value.

\textbf{Logical consistency.}
We checked logical consistency with the ELK reasoner v0.4.3 \cite{elk}
through OWL API v4.5.26, after merging the modules that ELK can process
into a single ontology. ELK supports only part of the OWL language, and
the modules also contain universal restrictions, inverse properties and
other constructs that ELK does not handle. The result therefore applies
only to the supported subset; an OWL profile report and a checked
projection of the ontology would be needed to define its logical scope
precisely. The taxonomy data and large reference modules were excluded.
