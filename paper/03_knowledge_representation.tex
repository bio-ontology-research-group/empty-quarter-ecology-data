\subsection{Knowledge representation}\label{ontology}

We developed a formal knowledge base to integrate the different types
of data generated in this project. The semantic layer encodes the
recorded provenance chain from physical sampling to digital data products,
supporting cross-domain queries and interoperability through shared
vocabularies.

\subsubsection{Architecture}

The knowledge base is constructed in Description Logic
\cite{dlhandbook} using a modular architecture that strictly separates
the terminology (Terminological Box, TBox, or ontology) from the
observed facts (Assertion Box, ABox, or domain knowledge). The TBox
uses OWL~2 \cite{owl2}, while the ABox contains the instance data
generated from the expeditions. The deployment uses separate named
graphs for the terminology, asserted expedition data, taxonomy
references and derived assertions. The current module-level entity
counts are reported in Section~\ref{records}; no historical
whole-graph count is used as a proxy for the regenerated package.

\subsubsection{Prefixes used in listings}\label{subsec:prefixes}

For brevity, the Turtle and SPARQL listings throughout the paper use
the prefix declarations of Table~\ref{tab:prefixes}; these
declarations should be prepended to any listing that the reader
wishes to execute against a local or deployed graph. For example, the full
IRI \texttt{https://rubalkhali.science/kb/RAK\_P100001} is written
\texttt{rak:P100001}, and
\texttt{http://semanticscience.org/resource/SIO\_000291} is written
\texttt{sio:000291}. The separate \texttt{rak\_kb:} prefix covers the same
knowledge-base namespace without the \texttt{RAK\_} local-name prefix. It is
needed for one legacy individual, the PowerSoil extraction protocol
\texttt{rak\_kb:DNA\_ext\_powersoil}, which is the only individual in the
released graph minted without the \texttt{RAK\_} prefix; every other protocol
individual (for example \texttt{rak:L000010},
\texttt{rak:L\_Surface\_Lab}) follows the prefixed convention. The
inconsistency is recorded here rather than silently corrected because
changing the IRI would break the checksums of the already-validated
modules.

\subsubsection{Ontology engineering and design patterns}

We use the Semanticscience Integrated Ontology (SIO) \cite{sio} as the
upper-level framework. SIO provides general-purpose classes and
relations applicable across scientific domains, supporting semantic
interoperability with other SIO-based datasets. We defined all
domain-specific classes as subclasses of SIO classes, and all
introduced relations are sub-relations of SIO relations. We mapped
classes to SIO and maintained full semantic mappings in our public
repository (see Section~\ref{code}).

The canonical terminology module
(\path{ontology/rubalkhali.owl}) declares 333 classes: 297
project-local \texttt{RAK\_} classes and 36 referenced classes (32 SIO
and four PATO). It also declares 20 object properties (11
project-local and nine SIO properties) and 35 datatype properties
(34 project-local and one SIO property). These figures are declaration
counts from the staged canonical module; they are not counts of the
imported ontologies or of whole-graph OWL axioms. The release workflow
recounts the distinct serialized declaration IRIs, fails if they differ from
these values and records the result in
\path{evidence/semantic-validation/ontology_declaration_audit.json}.
\paragraph{Measurement pattern}

We model a quantitative measurement using SIO's ontology design
pattern for measurement processes: a measurement is a process that
generates a value for a specific quality of a target entity.

\begin{align}
	\label{eq:measurement}
	\text{MeasurementProcess} & \sqsubseteq \text{Process} \\
	\text{Quality} & \sqsubseteq \text{Attribute} \\
	\text{Quantity} & \sqsubseteq \text{InformationContentEntity} \\
\text{MeasurementProcess} & \sqsubseteq \exists \text{hasTarget}.\text{Entity} \sqcap \exists \text{hasOutput}.\text{Quantity} \\
\text{Quantity} & \sqsubseteq \exists \text{hasValue}.\text{xsd:double} \sqcap \exists \text{hasUnit}.\text{Unit} \\
\text{Quantity} & \sqsubseteq \exists \text{isMeasurementValueOf}.\text{Quality}
\end{align}

We identified all units with classes from the Units Ontology (UO)
\cite{uo}. Qualities are expressed using the Phenotype and Trait
Ontology (PATO) \cite{pato} and linked to SIO as subclasses of the
{\em Quality} class. To illustrate this pattern, we provide an
example represented in Turtle format. The example
(Listing~\ref{lst:ttl_temp}) demonstrates an environmental temperature
measurement taken at a sampling site.

\begin{lstlisting}[caption={Turtle representation of an environmental temperature measurement.}, label={lst:ttl_temp}, basicstyle=\ttfamily\scriptsize, frame=single]
rak:P000001 a rak:0000006 ; # Measurement Process
  sio:000068 rak:3000001 ; # isPartOf (site visit)
  sio:000139 rak:A000001 ; # hasAgent
  sio:000132 rak:D000002 ; # hasParticipant (device)
  sio:000229 rak:4000001 . # hasOutput (Value)

rak:3000001 a rak:0000003 ; # Site Visit
  sio:000291 rak:1000001 . # hasTarget (Sampling Site)

rak:4000001 a rak:0000010 ; # Quantity
  sio:000221 uo:0000027 ; # hasUnit (degree Celsius)
  rak:2000003 "20.7"^^xsd:double ; # hasValue
  sio:000215 rak:5000001 . # isMeasurementValueOf (Quality)

rak:5000001 a pato:0000146 ; # Temperature Quality
  sio:000011 rak:1000001 ; # isAttributeOf
  sio:000216 rak:4000001 . # hasMeasurementValue
\end{lstlisting}

In words, an instance \texttt{rak:P000001} of a measurement
process is part of the site visit \texttt{rak:3000001}, which in turn has
the sampling site \texttt{rak:1000001} as its target, and the process
produces as output the quantity \texttt{rak:4000001}. The target edge on
the process itself is not asserted: the terminology declares the property
chain $\text{isPartOf} \circ \text{hasTarget} \sqsubseteq
\text{hasTarget}$, so \texttt{rak:P000001 sio:000291 rak:1000001} is
entailed rather than stored. A query that must run without reasoning
should therefore traverse the visit explicitly. The visit individual is
not redundant bookkeeping: it carries the campaign and the exact
date-time at which the reading was taken, so repeated visits to one site
across campaigns remain distinguishable. That
quantity carries the literal value \texttt{20.7}, is reported in
degrees Celsius (\texttt{uo:0000027}), and is the measurement
value of a temperature quality \texttt{rak:5000001}, which is in turn
an attribute of the
same site. In SIO, \texttt{sio:000215} is the value-to-quality
relation and \texttt{sio:000216} is its quality-to-value inverse.
Reading the chain in either direction therefore connects
the numeric reading to both the measured site and the abstract quality
that it quantifies.

Archived-soil pH uses the same four-individual measurement pattern without
treating an archived-soil assay as a field-site observation. The existing
specimen bears an acidity quality (PATO:0001842) through
\texttt{sio:000008}. A value individual is typed as both SIO measurement value
(SIO:000070) and pH (SIO:001089), carries its numeric literal through
\texttt{sio:000300}, and has unit UO:0000196. The value points to the quality
with \texttt{sio:000215} and to the measuring process with
\texttt{sio:000232}; the quality points back with \texttt{sio:000216}. The
SIO measuring process (SIO:001054) consumes and targets the specimen, outputs
the value, is specified by the CaCl$_2$ protocol, has the instrument as a
participant, and is part of a dated measurement session. Source-workbook and
session provenance remain connected to the process. Rows that fail source,
date, specimen or quality-control admission remain in the audit table and are
not asserted as measurements.
\paragraph{Sampling site and biome assignment pattern}

Each physical sampling location is represented as a persistent
individual that is grounded in the Environment Ontology (ENVO) by
linking to a biome and to one or more environmental features. An
existential restriction requires a biome filler, while a universal
restriction constrains every such filler to the ENVO biome class.
Under OWL's open-world semantics this does not make the asserted ENVO
biome class the unique possible filler. Because ShEx
shapes match triple patterns and the biome and feature assignments are
encoded as class restrictions rather than as simple triples, no shipped
shape tests biome completeness. Closed-world completeness is instead
enforced by a separate query gate,
\path{scripts/validation/validate_site_biome_completeness.py}, which
fails if any \texttt{rak:0000002} individual lacks a
\texttt{rak:2000001} or \texttt{rak:2000002} restriction.

\begin{align}
	\label{eq:site}
	\text{SamplingSite} & \sqsubseteq \text{Site} \\
	\text{SamplingSite} & \sqsubseteq \exists
	    \text{hasBiome}.\text{ENVO:Biome} \sqcap \forall
	    \text{hasBiome}.\text{ENVO:Biome} \\
	\text{SamplingSite} & \sqsubseteq
	    \begin{aligned}[t]
	    &\exists \text{hasEnvironmentalFeature}.{}\\[-0.25ex]
	    &\text{ENVO:EnvironmentalFeature}
	    \end{aligned}
\end{align}

\begin{lstlisting}[caption={Turtle representation of a sampling site grounded in ENVO.}, label={lst:ttl_site}, basicstyle=\ttfamily\scriptsize, frame=single]
rak:1000001 a rak:0000002 ; # Sampling Site
  rdfs:label "Site 1" ;
  geo:asWKT
    "POINT(45.166511388888885 19.149770555555556)"^^geo:wktLiteral ;
  a [ a owl:Restriction ;
      owl:onProperty rak:2000001 ;        # hasBiome
      owl:someValuesFrom envo:01000179 ], # desert biome
    [ a owl:Restriction ;
      owl:onProperty rak:2000002 ;        # hasEnvironmentalFeature
      owl:someValuesFrom envo:01000018 ]. # gravel
\end{lstlisting}

In words, the sampling site \texttt{rak:1000001} carries a label and a
WKT geometry as ordinary data properties, and its biome and
environmental feature are encoded as OWL class restrictions on the
individual rather than as direct object-property assertions. This
matters for reuse: a query of the form \texttt{?s rak:2000001 ?biome}
returns no rows against the asserted graph. A reader must either match
the restriction structure, as in

\begin{lstlisting}[caption={SPARQL pattern that recovers the biome of a sampling site from the asserted restriction structure.}, label={lst:sparql_biome}, basicstyle=\ttfamily\scriptsize, frame=single]
?site a rak:0000002 ;
      a [ owl:onProperty rak:2000001 ;
          owl:someValuesFrom ?biome ] .
\end{lstlisting}

\noindent or query a materialized graph in which the restriction has
been expanded. The combined existential and universal restriction on
\texttt{hasBiome} (Equation~\ref{eq:site}) does not identify a unique
biome filler. Under OWL's open-world semantics it requires at least one
\texttt{hasBiome} value in the named ENVO class and constrains every
such value to that class; it does not entail that the site has only one
biome filler. The recorded environmental feature for Site~1 is the ENVO
material \emph{gravel} (\texttt{envo:01000018}); features are drawn
from the project's own code table, which maps free-text field
descriptors to ENVO identifiers, and a feature is therefore a recorded
surface descriptor rather than a curated landform classification.

\paragraph{Laboratory-control pattern}

A laboratory control is represented as an occurrence-specific material
entity, not as a property of an expedition and not as the string used to
label a library. The material bears its own instance of a positive,
negative, extraction-blank or PCR-blank role through
\texttt{sio:000228} (\emph{has role}); the inverse
\texttt{sio:000227} is asserted explicitly. A laboratory process takes
the material as input and target through \texttt{sio:000230} and
\texttt{sio:000291}, produces the derived material or dataset through
\texttt{sio:000229}, and realizes the role through
\texttt{sio:000355}. The inverse input, target, output and realization
directions are also asserted because the deployed validation and query
paths do not assume complete inverse-property materialization.

An extraction or PCR process is linked by \texttt{sio:000068}
(\emph{is part of}) to its processing batch. Biological materials
processed in the same batch retain their own expedition provenance;
neither the blank nor the batch receives a direct trip link. This is
essential here because an extraction day could contain samples from
several trips. Whole-cell D6300 and purified-DNA D6322 controls enter
the workflow at different processes, so the graph can distinguish
extraction and lysis evaluation from PCR, library and sequencing
evaluation. A product is linked to its manufacturer composition
specification by \texttt{sio:000339} (\emph{is specified by}), with
\texttt{sio:000338} asserted in the reverse direction. Each expected taxon
is both a promoted specification-to-taxon fact and a reified,
evidence-bearing expected-taxon assertion. Manufacturer genomic-DNA
percentages, their unit IRIs and composition basis remain in the normalized
table rather than being represented as expected 16S read fractions in RDF.

Uncertain identity, batch membership and assay applicability are
represented as SIO statements linked to source evidence with
\texttt{sio:000772}; they carry an explicit confirmed, provisional,
unresolved or inapplicable status. Each material occurrence has a
separate role individual, and reused labels are represented as aliases,
preventing functional role relations from merging physical controls.
No sterile-bag role class or material instance is asserted. An unresolved
inventory disposition records that bag identifiers and sequence occurrences
were unavailable; the model can be extended if an inventory is recovered.
A machine-checked D6300 composition and expected-taxon example is provided in
Supplementary Section~S1.

\paragraph{Patterns specified in the supplement}

The measurement, sampling-site and laboratory-control patterns above are
reproduced here because they carry contracts a reuser must know: the
value--quality direction, the restriction encoding of biome and environmental
feature, and the separation of control material, role, process and evidence.
The remaining six patterns (sampling, protocol execution, taxonomic
abundance, XRF geochemistry, the sequencing chain and sequencing quality control) are
specified with their axioms and machine-checked worked examples in
Supplementary Section~S1. Full generator sources, the complete class and
property mappings and the shape files are distributed with the package
(Section~\ref{records:files}).

We use OpenLink Virtuoso \cite{virtuoso} for RDF storage and query
answering. In a development benchmark, a project-specific
forward-rule program applied selected RDFS/OWL rules for subclass,
subproperty, domain, range, inverse, symmetric, equivalence and
transitive-property assertions. The program used three scheduled
passes, including only a one-hop transitive pass. It did not
demonstrate convergence to a fixed point and did not implement
arbitrary OWL property chains. We therefore describe this output as a
\emph{selected rule expansion}, not as complete OWL-Horst
\cite{owlhorst} closure.

The current staged package contains the regenerated asserted modules
but no validated materialized whole-graph artifact. We consequently
report exact module-level entity counts rather than historical
asserted or inferred triple counts. The selected rule expansion has
not been demonstrated to reach a zero-delta fixed point and does not
implement arbitrary property chains; neither complete OWL-Horst
coverage nor a complete inferred-graph count is claimed.
\subsubsection{Schema definition}\label{subsec:schema_def}

We used Shape Expressions (ShEx) \cite{shex} to define structural
schemas for the core entity types. While OWL provides open-world
reasoning and inference capabilities, it cannot readily enforce data
completeness constraints. We developed ShEx schemas to explicitly
validate the graph's structure, supporting data-quality and conformance checks
before loading it into the database.

Our ShEx implementation defines shapes for Sampling Sites, Soil
Samples, Environmental Measurements, DNA Extracts, and Sequencing
Datasets. These shapes require the declared attributes on conforming nodes.
For instance, Listing~\ref{lst:shex_site} shows how the schema requires every
conforming Sampling Site to be explicitly typed, labelled and georeferenced,
while optionally capturing a textual description.

\begin{lstlisting}[caption={ShEx shape for Sampling Site validation.}, label={lst:shex_site}, basicstyle=\ttfamily\scriptsize, frame=single]
<#SamplingSiteShape> {
    rdf:type [rak_kb:RAK_0000002] ; # Must be a Sampling Site
    rdf:type . * ;                  # May have other inferred types
    rdfs:label . ;                  # Must have a label
    dcterms:description xsd:string ? ; # Optional description
    geo:asWKT . ;                   # Must have coordinates
}
\end{lstlisting}

In words, the shape \texttt{<\#SamplingSiteShape>} requires that
every conforming node carry an explicit type assertion to
\texttt{rak:0000002} (Sampling Site), an \texttt{rdfs:label} and a WKT
geometry; it permits any number of additional inferred types and
optionally allows a free-text description. Coordinates are mandatory in
the shape, in the Methods contract of
Section~\ref{methods} and in the staged copy of the shape;
all 70 sampling-site individuals in the released module satisfy it. A
site record that omits the mandatory type, label or geometry is
rejected before it reaches the triple store, and a deliberately
coordinate-free fixture is included in the negative fixture suite
(Section~\ref{valid}) to prove that the rejection actually
fires. Note that the shape file declares
\texttt{rak\_kb:} for the bare knowledge-base namespace, so the
sampling-site class is written \texttt{rak\_kb:RAK\_0000002} there and
\texttt{rak:0000002} in the Turtle listings above; the two forms denote
the same IRI.
